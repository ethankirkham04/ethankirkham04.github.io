Before this assignment, I mostly thought coding standards were about making code look clean. I thought they were things like using the right number of spaces, putting braces in the correct place, or keeping everything formatted the same way. After using ESLint in VSCode, I started to realize that coding standards are more important than just appearance. They can help catch mistakes, make code easier to read, and even teach you better habits while learning a programming language.

## More Than Just Formatting

At first, I thought coding standards were mostly there to make everyone's code look similar. I did not really see why small things like spacing, quotation marks, or variable names mattered that much as long as the program worked.

After working with TypeScript more, I started to understand why consistency is useful.

When code is written in a clear and organized way, it is much easier to understand what is happening. For example, a variable named `x` might make sense while I am writing the program, but a name like `totalScore` or `studentCount` makes the purpose much easier to understand later.

This becomes even more important when multiple people are working on the same project. If everyone writes code in a completely different style, it can become harder to read and maintain. Coding standards give everyone a common way to write code so that the project feels more consistent.

## My Experience With ESLint

My first experience with ESLint was a little frustrating.

There were times when my code would run correctly and give me the exact output I expected, but ESLint would still show errors or warnings. At first, I would think that if the code works, then why do I still need to change it?

After using ESLint more, I started to understand that code working does not always mean the code is written well.

Some ESLint errors are simple formatting problems, but others point out things that could make the code confusing or cause problems later. It also forces me to pay attention to parts of my code that I might normally ignore.

One thing I like about ESLint is that it gives feedback while I am coding. Instead of finishing an entire program and then finding out that there are problems, I can see warnings directly in VSCode and fix them as I go.

## Learning Through Coding Standards

I also think coding standards can help someone learn a programming language.

TypeScript is still newer to me compared to Python, C, and C++. Because of that, I sometimes write TypeScript using habits that I learned from other languages.

ESLint helps point out when I am doing something that might not be the normal or recommended way to write TypeScript. Even if I do not understand the warning at first, looking into why it appears can teach me something new about the language.

I think that is one of the most useful parts of coding standards. They are not only rules about how code should look. They can also show you how programmers are expected to write code in a certain language.

Instead of only learning how to make code run, I am also learning how to make it easier for other people to understand.

## The Annoying Part

Even though I understand why ESLint is useful, I still think fixing every error can sometimes be annoying.

There have been times when I thought I was completely finished with an assignment because the output was correct, and then I noticed that ESLint still had several complaints.

It can feel frustrating to go back and change code that already seems to work.

At the same time, I think that frustration is part of learning better habits. If I always ignore warnings because my program works, I might keep making the same mistakes in larger projects.

The important thing is not to blindly change the code just to make the red lines disappear. I think it is better to understand what the warning means and why ESLint wants the code changed. That way, I can recognize the same problem the next time.

## Why Coding Standards Matter

The biggest thing I learned from using ESLint is that writing code is not only about getting the correct answer.

Readable and organized code also matters.

This is especially important in software engineering because code is often worked on by many different people. Someone else might need to understand my code, fix something, or add a new feature later.

Even if I am the only person working on the project, coding standards can still help. If I come back to my own code several months later, I might not remember exactly what I was thinking when I wrote it.

Clear code makes that process much easier.

## What I Learned

Before using ESLint, I probably would have said that coding standards were mostly about making programs look professional.

Now I think they are also about making code easier to understand, maintain, and improve.

ESLint can definitely be annoying when it finds problems in code that already seems to work, but I think it has helped me become more careful about how I write TypeScript.

Going forward, I want to focus less on only making my programs work and more on making sure they are also readable and organized.

Getting the right output is important, but writing code that another person can easily understand is also part of becoming a better programmer.
